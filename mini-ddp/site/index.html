mini-ddp

从一个最朴素的问题开始：如果一台机器训练太慢，能不能让几个“工人”各算一部分数据，最后得到和单个大批次训练一样的模型更新？这个网页会先解释每个新词，再对应到代码。

先把词说清楚

后面每个术语都只为解决一个具体问题出现。这里先给最小词典，避免把工程黑话当成解释。

参数 模型里会被训练改变的数字，比如线性层的权重。训练的结果，本质上就是这些数字被改成更合适的值。
梯度 每个参数应该往哪个方向改、改多少的信号。一次反向传播会为参数算出梯度。
模型副本 一份完整模型的拷贝。数据并行不是把模型切开，而是让多个完整副本看不同数据。
loss 损失值，表示模型这次预测错得有多严重。loss 越小，通常表示这批数据上预测越好。
反向传播 从 loss 往回计算每个参数梯度的过程。它回答“哪个参数该往哪个方向改”。
optimizer 优化器。它读取参数的梯度，然后真正修改参数，比如按学习率走一小步。
rank 工人的编号。rank 0、rank 1 就像“第 0 个工人”“第 1 个工人”，用于决定谁读哪份数据、谁负责发初始参数、通信时按什么顺序对齐。
bucket 梯度打包箱。它把多个参数的梯度放进一组，一次通信发一组，而不是每个小梯度都单独通信。
DDP Distributed Data Parallel，分布式数据并行。意思是：数据分给多个工人，模型每个工人一份，梯度同步后一起更新。
hook 自动触发的小回调。这里指“某个梯度刚算出来时，自动通知同步管理器”。
PyTorch 一个常用深度学习框架。这里的代码用它来定义模型、计算梯度、运行优化器。
CPU 和 MPS CPU 是普通处理器；MPS 是苹果芯片 GPU 的 PyTorch 加速接口。这个项目两种设备都能验证。
张量 多维数字数组。模型参数、输入数据和梯度在 PyTorch 里通常都是张量。
进程 操作系统里独立运行的一份程序。真实 DDP 通常让每个进程管理一个工人。

为什么要设计 rank？

先不要想 PyTorch。想象你要把 1 万张图片交给 4 个工人训练。系统至少要回答四个问题：谁是第几个工人？谁处理哪一段数据？谁的初始模型说了算？大家通信时按什么顺序对齐？rank 就是这四个问题的共同坐标。

没有 rank 会怎样？

如果所有工人都没有编号，大家可能重复拿同一批数据，也可能都以为自己该当“主工人”。训练会变成一群独立实验，而不是一个协同训练任务。

rank 解决了什么？

rank 是稳定编号。rank 0 可以负责把初始参数发给别人；rank 1 可以拿第 2 份数据；所有工人都按 rank 顺序参与梯度平均。

为什么每个 rank 要有完整模型？

因为这是数据并行：并行的是数据，不是模型结构。每个工人用完整模型看不同小批次，才能独立算出“这份数据希望模型怎么改”。

为什么 rank 0 的参数要广播？

广播就是“一人发给所有人”。如果初始参数不同，后面即使平均梯度，大家也会从不同起点出发，无法保持同一个模型。

代码里 rank 是怎么被用上的？

每次前向计算都显式传入 rank。这个编号决定调用哪一份模型副本；如果 rank 越界，代码直接报错，避免把数据送给不存在的工人。

def forward(self, rank: int, *args, **kwargs):
    if rank < 0 or rank >= self.world_size:
        raise IndexError(...)
    return self.replicas[rank](*args, **kwargs)

rank 0 为什么能当初始参数来源？

构造时先拷贝 rank 0 的状态，再加载到其他副本。这样所有工人从同一组参数数字开始，后面的梯度平均才有意义。

source_state = {
    key: value.detach().clone()
    for key, value in self.replicas[0].state_dict().items()
}
for replica in self.replicas[1:]:
    replica.load_state_dict(source_state)

为什么要同步梯度？

每个工人只看一部分数据，所以它算出的梯度只是局部意见。我们想要的不是某个工人的意见，而是“所有数据合起来”的意见。

全体数据的更新方向 = 所有工人的本地梯度求平均
第一步：切数据 一个大批次被切成几份，每个 rank 只拿自己的那份。这个动作叫数据分片，也就是把数据按工人编号分配。
第二步：各自反向传播 反向传播就是从 loss 回头算梯度。loss 是模型预测错了多少的数字，梯度说明参数该怎么改。
第三步：平均梯度 平均后，每个模型副本拿到同一份梯度。只要初始参数相同、更新规则相同，下一步参数仍然相同。

先切数据，再各算各的 loss

`shard_batch` 按第 0 维切开一个大批次。训练代码给每个 rank 一片数据，让每个模型副本独立算出自己的 loss。

xs = shard_batch(x, ddp.world_size)
ys = shard_batch(y, ddp.world_size)

losses = [
    F.cross_entropy(ddp(rank, xs[rank]), ys[rank])
    for rank in range(ddp.world_size)
]

梯度平均发生在哪里？

每个 rank 的同一个参数都有一份梯度。这里把它们搬到 CPU 上求平均，再写回每个副本的同名参数。

grads = [
    self.params_by_rank[rank][param_index].grad
    for rank in range(self.world_size)
]
averaged = torch.stack([
    grad.detach().to("cpu") for grad in grads
]).mean(dim=0)

为什么要有 bucket？

现在问题变成：模型可能有成千上万个参数张量，每个张量都有一个梯度。同步这些梯度时，是一个一个发，还是全部攒到最后发？两个极端都不好。

如果每个梯度单独通信

小消息太多。每次通信都有固定开销，像寄一万封很薄的信，邮费和排队时间会淹没真正内容。

如果所有梯度攒成一个超大包

要等最后一个梯度算完才能开始通信。这样反向传播期间网络闲着，最后大家一起等一个大包传完。

bucket 是中间方案

bucket 是“梯度打包箱”：把相邻的一组梯度凑成适中大小。某个打包箱装满并且里面的梯度都算好了，就可以先同步这一箱。

为什么这能更快？

反向传播还在继续算前面层的梯度时，后面层的 bucket 已经可以开始通信。计算和通信重叠，等待时间就少了。

所以 bucket 不是数学概念，而是系统设计概念：它不改变“平均梯度”的结果，只改变“什么时候、以多大粒度通信”。

bucket 在代码里只是参数下标分组

`parameter_indices` 记录这一箱包含哪些参数。`bytes` 记录这一箱大概多大，用来解释为什么要受 `bucket_cap_mb` 控制。

@dataclass(frozen=True)
class Bucket:
    index: int
    parameter_indices: tuple[int, ...]
    bytes: int

为什么按大小装箱？

代码从后往前扫描参数，当前箱子超过容量上限就开新箱。生产 DDP 也是为了让反向传播后面先出现的梯度尽早凑箱通信。

for param_index in reversed(range(len(reference_params))):
    param_bytes = _tensor_nbytes(reference_params[param_index])
    if current and current_bytes + param_bytes > cap_bytes:
        buckets_reversed.append(current)
        current = []
        current_bytes = 0
    current.append(param_index)

从设计映射到代码

`mini-ddp` 把真实多进程通信收缩到一个进程里的多个模型副本。这样 CPU 和 MPS 都能跑，读者可以专心看清楚 DDP 的语义。

创建多个模型副本

`MiniDDP.__init__` 深拷贝出 `world_size` 份模型。`world_size` 是工人总数，也就是 rank 的数量。

把 rank 0 的参数发给所有副本

`broadcast_parameters_and_buffers()` 保证所有副本从同一个模型开始。buffer 是模型里不由梯度更新、但也要同步的状态，比如某些归一化层保存的运行统计数字。

给每个参数放一个自动提醒

自动提醒就是 PyTorch 自动求导系统里的 hook：当某个参数的梯度被反向传播算出来时，hook 会记录“这个 rank 的这个参数已经 ready”。ready 的意思是“可以用于同步了”。

按 bucket 检查梯度是否到齐

`MiniReducer.synchronize()` 逐个 bucket 检查：这个打包箱里，每个 rank 的每个参数梯度都到了吗？没到就报错，避免悄悄用缺失梯度更新。

平均梯度并写回

对同一个参数，把所有 rank 的梯度取平均，再写回每个副本的 `param.grad`。`param.grad` 是 PyTorch optimizer 会读取的梯度位置。

hook 把“梯度已产生”变成事件

注册 hook 后，只要某个参数的梯度被算出来，`_ready` 就会记录这个 rank 和参数下标。后面同步时用它检查 bucket 是否真的到齐。

def _make_hook(self, rank: int, param_index: int):
    def hook(grad: Tensor) -> Tensor:
        bucket_index = self.param_to_bucket[param_index]
        self._ready.setdefault(bucket_index, set()).add(
            (rank, param_index)
        )
        return grad
    return hook

同步前先证明 bucket 完整

这个检查是教学实现里很重要的一步：如果某个参数没有参与反向传播，不会静默平均一个缺失的梯度，而是直接告诉你缺了谁。

expected = {
    (rank, param_index)
    for rank in range(self.world_size)
    for param_index in bucket.parameter_indices
}
missing = expected - self._ready.get(bucket.index, set())
if missing:
    raise RuntimeError(...)

mini-ddp 和 PyTorch DDP 的边界

真实 PyTorch DDP

  • 通常一个进程管理一个设备上的一个模型副本。
  • ProcessGroup 是通信小组，负责让不同进程互相发送参数和梯度。
  • all-reduce 是“所有人贡献一个张量，所有人拿到聚合结果”的通信动作。DDP 用它来求平均梯度。
  • Reducer 是梯度同步管理器，负责 bucket、hook、通信顺序和写回梯度。

这个教学实现

  • 一个进程里放多个模型副本，避免安装和启动真实分布式后端。
  • 用 Python 张量平均模拟 all-reduce 的平均值，保留数学效果。
  • 保留 hook 和 bucket ready 检查，但不实现异步通信重叠。
  • 可以在 CPU 或 Apple MPS 上验证，适合逐行阅读。

运行验证
